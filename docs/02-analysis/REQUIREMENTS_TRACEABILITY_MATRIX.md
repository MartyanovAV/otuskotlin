# Requirements Traceability Matrix

Документ связывает утверждённый MVP FitBridge с бизнес-требованиями, аналитическими требованиями и будущими приёмочными проверками. Канонический бизнес-источник MVP: [BR-010-public-plan-link-mvp.md](../01-business/BR/BR-010-public-plan-link-mvp.md).

## Статус

| Параметр | Значение |
|---|---|
| Статус | Утверждена для MVP / справочный источник трассировки |
| Область | Gate 1 MVP с публичной ссылкой на тренировочный план |
| MVP-путь | `Trainer-first public plan link` |
| Зарегистрированный пользователь MVP | Только тренер |
| Незарегистрированный пользователь MVP | Клиент, открывающий публичную ссылку на план |
| Источники | `docs/01-business`, `docs/02-analysis`, `docs/03-architecture/api` |

Матрица фиксирует только текущий MVP. Регистрация клиента, клиентский кабинет, `AccessGrant`, multi-specialist, биллинг, библиотека упражнений, продвинутая аналитика, чат, медданные, фото/видео и переносимость истории между тренерами относятся к Phase 2 / out of scope.

## Правила чтения

| Поле | Значение |
|---|---|
| Trace ID | Стабильный идентификатор строки трассировки |
| MVP capability | Проверяемая возможность MVP |
| Funnel stage | Этап воронки MVP |
| BR / AC | Бизнес-требование, user story и acceptance criteria |
| FR / NFR | Ссылки на функциональные и нефункциональные требования по номерам разделов |
| Tests | Планируемые приёмочные проверки и критерии автоматизации |
| Status | Готовность трассировки: `Ready`, `Needs detail`, `Gap` |

## Coverage By MVP Funnel

| Этап воронки | Covered traces | Gate 1 acceptance focus |
|---|---|---|
| trainer signup | `RTM-001` | Тренер может стартовать как единственный зарегистрированный пользователь |
| client card | `RTM-002` | Карточка создаётся тренером без регистрации клиента |
| plan | `RTM-003` | План связан с клиентской карточкой и достаточно прост для MVP |
| public link sent/opened | `RTM-004`, `RTM-005`, `RTM-009` | Ссылка даёт доступ только к конкретному плану и открывается без клиентского аккаунта |

| trainer review | `RTM-007`, `RTM-008`, `RTM-010` | Тренер видит статус, может закрыть ссылку и оценить ценность сценария |

## Известные разрывы и заметки поддержки

| Gap | Impact | Recommended action |
|---|---|---|
| Нет отдельного аналитического события для каждого шага воронки | Сложнее интерпретировать drop-off между созданием карточки, планом, открытием ссылки и отметкой выполнения | Перед инструментированием согласовать минимальный event taxonomy без расширения продуктового scope |
| Нет машинно-проверяемых API contracts | Тесты пока можно трассировать только до markdown-методов | Добавить OpenAPI/JSON Schema или единый request/response/error contract на архитектурном этапе |
| Метрики completion могут искажаться внешним каналом отправки ссылки | Невозможно точно отличить «ссылка не отправлена» от «клиент не открыл» без ручной фиксации тренером | В пилоте собирать качественную обратную связь тренера и не трактовать open rate как чистый UX-сигнал |
| Phase 2 client-owned модель не должна попадать в MVP через трассировку | Риск scope creep и ложных требований к регистрации клиента | Все строки, связанные с клиентским аккаунтом, `AccessGrant`, кабинетом и переносимой историей, держать вне MVP до отдельного решения |

## Maintenance Rules

1. Каждое новое MVP-требование должно получить строку `RTM-*` и ссылку на [BR-010](../01-business/BR/BR-010-public-plan-link-mvp.md) или другой утверждённый BR.
2. В MVP path не добавляются клиентская регистрация, клиентский кабинет и `AccessGrant` без отдельного изменения scope.
3. При автоматизации приёмки колонка `Tests` должна содержать test class/method references вместо плановых `TEST-*`.
4. Phase 2 требования остаются в матрице только если они влияют на MVP как constraint, gap или manual validation.
