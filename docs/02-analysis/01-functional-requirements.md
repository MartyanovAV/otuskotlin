# Функциональные требования FitBridge

Документ фиксирует требования текущего trainer-only MVP «Дневник тренера». Канонический бизнес-источник: [BR-010-trainer-diary-mvp.md](../01-business/BR/BR-010-trainer-diary-mvp.md).

## 1. Регистрация и рабочий контур тренера

### 1.1. Регистрация и аутентификация тренера

- **Источник требования:** `BR-006-trainer-onboarding.md`, `BR-010-trainer-diary-mvp.md`.
- **Описание требования:** Тренер регистрируется в Keycloak с уникальным username и входит по username. Форма явно сообщает, что создаётся аккаунт тренера; роль `TRAINER` назначается сервером.
- **Приоритет требования:** Высокий / MVP.

### 1.2. Приватный доступ к рабочему контуру

- **Источник требования:** `BR-002-access-control.md`, `BR-009-consent-privacy-deletion.md`.
- **Описание требования:** Все операции с клиентскими карточками и тренировочными планами доступны только principal с ролью `TRAINER`; ownership вычисляется по `JWT.sub`. Публичные и клиентские endpoints отсутствуют.
- **Приоритет требования:** Высокий / MVP.

## 2. Клиентские карточки

### 2.1. Создание минимальной ClientCard

- **Источник требования:** `BR-010-trainer-diary-mvp.md`, `US-R010-001`.
- **Описание требования:** Тренер создаёт минимальную карточку клиента без регистрации клиента и без client-owned профиля.
- **Приоритет требования:** Высокий / MVP.

### 2.2. Поиск и просмотр ClientCard

- **Источник требования:** `BR-010-trainer-diary-mvp.md`, `US-R010-002`.
- **Описание требования:** Тренер получает только принадлежащую ему карточку по идентификатору и ищет свои карточки по поддерживаемым фильтрам.
- **Приоритет требования:** Высокий / MVP.

### 2.3. Изменение и архивирование ClientCard

- **Источник требования:** `BR-010-trainer-diary-mvp.md`, архитектурный API-контракт.
- **Описание требования:** Тренер может исправить данные своей карточки и убрать неактуальную карточку из активного рабочего списка через архивирование. Физическое удаление не требуется.
- **Приоритет требования:** Средний / supporting MVP operation.

## 3. Тренировочные планы

### 3.1. Создание TrainingPlan

- **Источник требования:** `BR-010-trainer-diary-mvp.md`, `US-R010-003`.
- **Описание требования:** Тренер создаёт простой план, связанный с принадлежащей ему `ClientCard`, и добавляет минимальный набор элементов тренировки.
- **Приоритет требования:** Высокий / MVP.

### 3.2. Поиск и просмотр TrainingPlan

- **Источник требования:** `BR-010-trainer-diary-mvp.md`, `US-R010-004`.
- **Описание требования:** Тренер получает только принадлежащий ему план по идентификатору и ищет свои планы по поддерживаемым фильтрам, включая карточку клиента и статус.
- **Приоритет требования:** Высокий / MVP.

### 3.3. Изменение и архивирование TrainingPlan

- **Источник требования:** `BR-010-trainer-diary-mvp.md`, архитектурный API-контракт.
- **Описание требования:** Тренер изменяет содержимое своего плана и переводит неактуальный план из `ACTIVE` в `ARCHIVED`; отметка выполнения и `COMPLETED` отсутствуют.
- **Приоритет требования:** Средний / supporting MVP operation.

## 4. Авторизация и границы данных

### 4.1. Проверка ownership

- **Источник требования:** `BR-002-access-control.md`, `BR-009-consent-privacy-deletion.md`, `SECURITY_ARCHITECTURE.md`.
- **Описание требования:** Backend проверяет JWT и владение объектом для каждой read/write операции. Идентификатор объекта не является доказательством права доступа.
- **Приоритет требования:** Высокий / MVP.

### 4.2. Минимизация данных

- **Источник требования:** `BR-009-consent-privacy-deletion.md`, `DATA_CLASSIFICATION_MATRIX.md`.
- **Описание требования:** MVP хранит только данные, необходимые для работы тренера с карточками и планами, и не собирает медданные, фото/видео, замеры и расширенный client-owned профиль.
- **Приоритет требования:** Высокий / MVP.

### 4.3. Безопасное логирование

- **Источник требования:** `BR-009-consent-privacy-deletion.md`, `SECURITY_ARCHITECTURE.md`.
- **Описание требования:** Технические логи содержат идентификаторы корреляции, тип операции и результат, но не персональные поля и не содержимое карточек или планов.
- **Приоритет требования:** Высокий / MVP.

## 5. Операционная поддержка пилота

### 5.1. Поддержка без продуктовой ADMIN-роли

- **Источник требования:** `BR-002-access-control.md`, `BR-009-consent-privacy-deletion.md`.
- **Описание требования:** В MVP нет in-product admin/support интерфейса. Допустимы контролируемые операции пилота по runbook без broad bypass к domain API и без чтения пользовательских данных.
- **Приоритет требования:** Средний / MVP constraint.

## 6. Проверка продуктовой гипотезы

### 6.1. Измерение критического пути

- **Источник требования:** `BR-010-trainer-diary-mvp.md`, `BUSINESS_VISION.md`.
- **Описание требования:** Пилот измеряет регистрацию тренера, создание первой клиентской карточки, создание первого плана и возврат к поиску/просмотру карточек и планов.
- **Приоритет требования:** Высокий / MVP validation.

### 6.2. Ручная проверка willingness-to-pay

- **Источник требования:** `BR-007-billing-subscriptions.md`, `MONETIZATION_STRATEGY.md`.
- **Описание требования:** Встроенный биллинг не входит в MVP; готовность платить фиксируется через интервью и пилотные договорённости после прохождения критического пути.
- **Приоритет требования:** Средний / MVP validation.

## 7. Out of Scope / Phase 2

Следующие темы не являются функциональными требованиями текущего MVP:

- регистрация клиента, клиентский кабинет и client-owned профиль;
- публичные ссылки, capability-token и любой иной клиентский доступ к плану;
- отметки выполнения тренировок и состояние `COMPLETED`;
- `AccessGrant`, подтверждение/отзыв доступа и granular permissions;
- multi-specialist, командные сценарии и переносимость истории;
- биллинг, тарифы, лимиты, автоплатежи и dunning;
- библиотека упражнений, шаблоны и AI-генерация;
- продвинутая аналитика, отчёты, графики и экспорт;
- чат, отдельные push/email-уведомления и lifecycle communications;
- медданные, фото/видео, rich-media и body metrics.

Возврат любой из этих возможностей в разработку требует отдельного решения по scope, обновления BR/RTM и архитектурного решения до изменения публичного API.
