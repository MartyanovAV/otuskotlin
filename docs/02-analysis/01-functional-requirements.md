# Функциональные требования FitBridge

Документ фиксирует функциональные требования для утверждённого MVP с публичной ссылкой на тренировочный план. Канонический бизнес-источник: [BR-010-public-plan-link-mvp.md](../01-business/BR/BR-010-public-plan-link-mvp.md).

## 1. Регистрация и рабочее пространство тренера

### 1.1. Регистрация тренера

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-006-trainer-onboarding.md`, `MVP_SCOPE_SUMMARY.md`.
- **Описание требования:** Система должна позволять зарегистрироваться тренеру как единственному зарегистрированному пользователю MVP и перейти к созданию первой клиентской карточки.
- **Приоритет требования:** Высокий / MVP.

### 1.2. Клиент без регистрации

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `CUSTOMER_PERSONAS.md`.
- **Описание требования:** Клиент не создаёт аккаунт, не входит в личный кабинет и не управляет профилем в MVP. Его единственный пользовательский сценарий — открыть публичную ссылку на конкретный план и оставить отметку выполнения.
- **Приоритет требования:** Высокий / MVP constraint.

## 2. Клиентская карточка

### 2.1. Создание `ClientCard` тренером

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `MVP_SCOPE_SUMMARY.md`.
- **Описание требования:** Тренер должен создать минимальную карточку клиента для ведения плана. Карточка не является клиентским аккаунтом и не требует регистрации клиента.
- **Приоритет требования:** Высокий / MVP.

### 2.2. Минимальность данных карточки

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `DATA_CLASSIFICATION_MATRIX.md`.
- **Описание требования:** В карточке используются только данные, необходимые тренеру для идентификации клиента в своём рабочем процессе. Медданные, фото/видео, body metrics, расширенные цели и переносимая история не входят в MVP.
- **Приоритет требования:** Высокий / MVP constraint.

## 3. Тренировочный план

### 3.1. Создание `TrainingPlan`

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-004-program-builder.md`.
- **Описание требования:** Тренер должен создать простой тренировочный план, связанный с `ClientCard`. План должен быть достаточным для того, чтобы клиент понял назначение и мог отметить выполнение.
- **Приоритет требования:** Высокий / MVP.

### 3.2. Ограничение конструктора плана

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-004-program-builder.md`.
- **Описание требования:** В MVP не входят библиотека упражнений, шаблоны, AI-генерация, продвинутые протоколы, медиа-вложения и сложные автоматизации.
- **Приоритет требования:** Высокий / MVP constraint.

## 4. Публичная ссылка на план

### 4.1. Получение публичной ссылки

- **Источник требования:** `BR-010-public-plan-link-mvp.md`.
- **Описание требования:** После создания плана тренер должен получить публичную ссылку на конкретный `TrainingPlan` и отправить её клиенту вне продукта.
- **Приоритет требования:** Высокий / MVP.

### 4.2. Закрытие доступа по ссылке

- **Источник требования:** `BR-010-public-plan-link-mvp.md`.
- **Описание требования:** Тренер должен иметь возможность закрыть доступ по публичной ссылке. После закрытия клиент не должен видеть план по этой ссылке.
- **Приоритет требования:** Высокий / MVP.

## 5. Просмотр плана клиентом

### 5.1. Открытие плана без регистрации

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `CUSTOMER_PERSONAS.md`, `CJM.md`.
- **Описание требования:** Клиент должен открыть публичную ссылку без регистрации и увидеть минимально необходимый план. Публичная страница не должна раскрывать данные других клиентов, расширенный профиль тренера или чувствительные сведения.
- **Приоритет требования:** Высокий / MVP.

### 5.2. Поведение закрытой ссылки

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `CJM.md`.
- **Описание требования:** Если тренер закрыл ссылку, клиент должен увидеть понятное сообщение о недоступности плана без предложения зарегистрироваться как обязательного продолжения.
- **Приоритет требования:** Высокий / MVP.

## 6. Отметка выполнения

### 6.1. Создание `CompletionMark`

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-005-progress-analytics.md`.
- **Описание требования:** Клиент должен оставить простую отметку выполнения по публичной ссылке без регистрации. Отметка связана с конкретным планом и используется тренером для проверки статуса.
- **Приоритет требования:** Высокий / MVP.

### 6.2. Ограничение аналитики выполнения

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-005-progress-analytics.md`.
- **Описание требования:** В MVP фиксируется факт выполнения и базовый статус. Adherence-расчёты, графики, отчёты, экспорт, cohort-аналитика и прогнозы относятся к Phase 2.
- **Приоритет требования:** Высокий / MVP constraint.

## 7. Обзор статуса тренером

### 7.1. Просмотр статуса выполнения

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-005-progress-analytics.md`.
- **Описание требования:** Тренер должен видеть, оставил ли клиент отметку выполнения, и использовать этот статус для follow-up в привычном канале общения.
- **Приоритет требования:** Высокий / MVP.

### 7.2. Минимальная рабочая панель

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-006-trainer-onboarding.md`.
- **Описание требования:** Тренеру нужен минимальный список своих клиентских карточек и планов со статусом выполнения. Расширенные дашборды, уведомления и отчёты не входят в MVP.
- **Приоритет требования:** Высокий / MVP.

## 8. Privacy и данные

### 8.1. Минимизация публичного ответа

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-009-consent-privacy-deletion.md`, `DATA_CLASSIFICATION_MATRIX.md`.
- **Описание требования:** Публичная страница плана должна содержать только данные, необходимые для просмотра плана и отметки выполнения. Система не должна собирать медданные, фото/видео, body metrics и расширенную историю клиента в MVP.
- **Приоритет требования:** Высокий / MVP.

### 8.2. Операционная поддержка пилота

- **Источник требования:** `MVP_SCOPE_SUMMARY.md`, `BR-009-consent-privacy-deletion.md`.
- **Описание требования:** В MVP нет отдельного in-product admin/support интерфейса. Операционная поддержка пилота допускается только как контролируемый процесс вне пользовательского продукта и не должна раскрывать чувствительные данные.
- **Приоритет требования:** Средний / MVP constraint.

## 9. Проверка коммерческой гипотезы

### 9.1. Ручная проверка willingness-to-pay

- **Источник требования:** `BR-010-public-plan-link-mvp.md`, `BR-007-billing-subscriptions.md`, `MONETIZATION_STRATEGY.md`.
- **Описание требования:** Встроенный биллинг не входит в MVP. Готовность платить проверяется через интервью, пилотные договорённости и ручную фиксацию результата после прохождения критического пути.
- **Приоритет требования:** Средний / MVP validation.

## 10. Out of Scope / Phase 2

Следующие темы не являются функциональными требованиями MVP:

- регистрация клиента и клиентский кабинет;
- клиентский дневник как самостоятельный продуктовый путь;
- `AccessGrant`, клиентское подтверждение доступа и отзыв доступа клиентом;
- multi-specialist и командные сценарии;
- биллинг, тарифы, лимиты, автоплатежи и dunning;
- библиотека упражнений, шаблоны и AI-генерация;
- продвинутая аналитика, отчёты, графики и экспорт;
- чат, отдельные push/email-уведомления и lifecycle communications;
- медданные, фото/видео, rich-media и body metrics;
- переносимость истории между тренерами.

## 11. Связь с Phase 2 client-owned моделью

MVP с публичной ссылкой проверяет trainer-first ценность как узкий validation wedge. После подтверждения метрик может быть отдельно спроектирована client-owned модель Phase 2: клиентский аккаунт, профиль, управление доступами, переносимая история и несколько специалистов. Эти возможности не должны попадать в MVP без отдельного бизнес-решения.
