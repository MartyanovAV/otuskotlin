## Назначение

Матрица фиксирует, какие данные FitBridge считаются публичными, внутренними, персональными, связанными со здоровьем, специальной категорией, платёжными или security-данными. Документ используется для согласований, проектирования доступа, логирования, процессов хранения/удаления и контроля границ MVP.

Связанные источники:

- `docs/01-business/BR/BR-009-consent-privacy-deletion.md` — согласия, приватность и удаление профиля;
- `docs/02-analysis/02-nonfunctional-requirements.md` — NFR 3.1–3.5, 8.1–8.2, 10.2;
- `docs/03-architecture/ERD.md` — MVP-сущности, ownership, soft delete и Phase 2 entities;
- `docs/03-architecture/ADR/ADR-006-use-opensearch-fluent-bit-observability.md` — правила masked structured logs и audit-oriented logging.

## Легенда классификации

| Класс | Значение для продукта |
|---|---|
| `public` | Данные, которые пользователь осознанно публикует или показывает другим пользователям в рамках профиля. |
| `internal` | Служебные данные продукта: статусы, технические идентификаторы, связи, версии, даты. |
| `personal` | Персональные данные: идентификация, контактные данные, профильные сведения. |
| `health-adjacent` | Фитнес-данные, связанные с состоянием, прогрессом, нагрузкой или самочувствием. |
| `special category` | Данные, которые могут требовать режима специальной категории по 152-ФЗ из-за связи со здоровьем, состоянием тела или биометрическим/медийным контекстом. |
| `payment` | Платёжные и подписочные данные Phase 2. |
| `security` | Токены, хэши, scope, события доступа, audit/security-события. |

## Обязательные продуктовые правила

1. В MVP есть два полноценных пути: `Trainer-led` и `Solo-client`; оба используют одинаковые правила согласий, доступа и логирования для профиля, дневника и программ.
2. `gender` и `goals` входят в MVP profile data как необязательные поля: они могут помогать trainer-led и solo-client планированию, но не должны увеличивать friction и не должны блокировать onboarding без отдельного явного решения о required-статусе.
3. `heightCm` не входит в MVP required/supported profile fields и переносится в Phase 2 / later measurement and body metrics scope.
4. Фото, видео и другие rich-media материалы не входят в MVP; допускаются только как Phase 2 / design reserve после отдельного решения по privacy, storage, стоимости и лимитам.
5. `AuditEvent` и `Notification` как продуктовые сущности не входят в MVP; MVP использует pull-model UI и infrastructure audit-oriented logging по ADR-006.
6. Любая операция с health-adjacent или special category данными должна быть private by default, deny by default и не должна раскрывать raw payload в логах.
7. При отзыве согласия, запросе удаления или архивировании профиля доступ тренеров и специалистов должен блокироваться немедленно, даже если физическая retention отдельных служебных следов продолжается по legal/security основаниям.

## Открытые вопросы для Phase 2

| Вопрос | Почему важно |
|---|---|
| Точные сроки хранения логов OpenSearch и будущих `AuditEvent` | Нужен баланс между расследованием инцидентов и минимизацией персональных данных. |
| Granular consent по типам данных и специалистам | Требуется для multi-specialist, замеров, медиа и командных сценариев. |
| Media retention: оригиналы, превью, CDN/cache, backup | Без этого нельзя безопасно включать фото/rich-media. |
| Payment data boundary | Нужно отделить данные FitBridge от данных платёжного провайдера и исключить хранение лишних реквизитов. |
| Самостоятельный экспорт и удаление данных | Требуется перед расширением privacy-модели Phase 2. |
