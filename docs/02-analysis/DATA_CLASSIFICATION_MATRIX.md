## Назначение

Матрица фиксирует, какие данные используются в утверждённом MVP и какие данные остаются за его пределами. Канонический бизнес-источник MVP: [BR-010-public-plan-link-mvp.md](../01-business/BR/BR-010-public-plan-link-mvp.md).

MVP работает по trainer-first модели: тренер — единственный зарегистрированный пользователь, клиент открывает публичную ссылку на конкретный план без регистрации и оставляет `CompletionMark`.

Связанные источники:

- `docs/01-business/BR/BR-010-public-plan-link-mvp.md` — канонический MVP;
- `docs/01-business/BR/BR-009-consent-privacy-deletion.md` — приватность и границы обработки данных;
- `docs/02-analysis/01-functional-requirements.md` — функциональные требования MVP;
- `docs/02-analysis/02-nonfunctional-requirements.md` — NFR по безопасности, логированию и UX.

## Легенда классификации

| Класс | Значение для продукта |
|---|---|
| `public-link-visible` | Данные, видимые клиенту по публичной ссылке на конкретный план. |
| `internal` | Служебные данные продукта: идентификаторы, статусы, даты, версии. |
| `personal` | Персональные данные или сведения, позволяющие идентифицировать человека. |
| `fitness-adjacent` | Фитнес-данные о плане и факте выполнения без медицинской диагностики. |
| `sensitive / special category` | Данные, которые могут требовать отдельного режима: медданные, body metrics, фото/видео, расширенные заметки о состоянии. |
| `security` | Токены, хэши, статусы публичного доступа, audit/security-события. |
| `payment` | Платёжные и подписочные данные Phase 2. |

## Матрица данных MVP и Phase 2

| Данные / поля | Классификация | Этап | Согласие / основание | Правила доступа | Правила логирования | Хранение / удаление |
|---|---|---|---|---|---|---|
| `TrainerAccount`: email/phone, auth subject, service terms acceptance | `personal`, `security` | MVP | Согласие тренера и пользовательские условия при регистрации. | Владелец-тренер и backend; клиент по публичной ссылке не видит контактные данные тренера, если они не включены в публичный минимум отдельным решением. | Не логировать email/phone/JWT; использовать internal ids и action/result. | Удаление/архивация по правилам аккаунта тренера и legal retention. |
| `TrainerProfile`: отображаемое имя тренера, базовое профессиональное описание | `personal`, частично `public-link-visible` | MVP, минимально | Согласие тренера на показ минимальной информации в контексте плана. | Тренер редактирует; клиент по ссылке видит только минимальный контекст, необходимый для доверия к плану. | Не логировать текст bio/описаний; допустимы ids. | Архивировать/скрывать при закрытии аккаунта или изменении публичной видимости. |
| `ClientCard`: displayName/псевдоним, внутренний id, статус карточки | `personal`, `internal` | MVP | Законная цель тренера вести клиента в рабочем контуре; не является клиентской регистрацией. | Видит только тренер-владелец; клиент по публичной ссылке видит только то имя/обозначение, которое необходимо для понимания плана, если оно включено в публичный минимум. | Не логировать raw displayName; использовать id и field names. | Удаление/архивация карточки по правилам тренерского рабочего пространства; не превращать в переносимый клиентский профиль без Phase 2 решения. |
| `TrainingPlan`: название, период, список тренировок/упражнений, базовые инструкции, статус | `fitness-adjacent`, `personal`, `internal`, частично `public-link-visible` | MVP | План создаёт тренер для клиентской карточки; клиент получает доступ через публичную ссылку. | Тренер-владелец видит и редактирует; клиент по ссылке видит только назначенный план. | Не логировать содержимое тренировок, инструкции и raw JSON; допустимы ids, version, status, action/result. | План хранится в рабочем контуре тренера; при закрытии ссылки публичный доступ прекращается. |
| Публичный access token / token hash / статус ссылки / дата закрытия | `security`, `internal` | MVP | Технический механизм доступа к конкретному плану; не является `AccessGrant`. | Raw token доступен только в ссылке; backend хранит hash/status; тренер может закрыть ссылку. | Raw token запрещён в логах; логировать только token id/hash prefix без восстановления, action/result и expiry/closed status. | Закрытые/истёкшие ссылки не должны раскрывать план; retention токенов минимизируется по security policy. |
| Public plan view event: openedAt, requestId, user agent class, coarse channel note if manually entered by trainer | `internal`, частично `security` | MVP validation | Нужен для измерения воронки; без скрытого профилирования клиента. | Доступно продуктовой аналитике в агрегированном виде и тренеру только как статус открытия, если это входит в MVP UI. | Не логировать IP как аналитический payload без отдельного решения; не хранить fingerprint. | Retention ограничить периодом пилота и задачами диагностики. |
| `CompletionMark`: статус выполнения, дата/время, необязательный короткий комментарий в пределах MVP | `fitness-adjacent`, `personal`, частично `public-link-visible` | MVP | Клиент добровольно оставляет отметку по публичной ссылке. | Тренер-владелец видит статус; клиент получает подтверждение сохранения на публичной странице. | Не логировать комментарий и raw payload; допустимы ids, status code, action/result. | Хранить как часть статуса плана; при закрытии ссылки публичный доступ прекращается, тренерский статус сохраняется. |
| Aggregated MVP funnel metrics: signup, card created, plan created, link opened, completion marked, trainer reviewed | `internal` | MVP validation | Используется для продуктовой аналитики без раскрытия лишних персональных данных. | PO/Product/Growth видят агрегаты; тренер видит только свои рабочие статусы. | В логах и аналитике использовать агрегаты и internal ids. | Retention по периоду пилота; не использовать для расширенной клиентской аналитики без Phase 2 решения. |
| Медданные, диагнозы, противопоказания, body metrics, замеры | `sensitive / special category`, `personal` | Out of scope / Phase 2 | Нужны отдельные согласия, юридическая проверка и продуктовая необходимость. | Не собираются и не показываются в MVP. | Не логировать, потому что не должны попадать в MVP payload. | Требуется отдельная retention/deletion policy перед включением. |
| Фото, видео, rich-media, EXIF и медиа-ссылки | `sensitive / special category`, `personal`, `security` | Out of scope / Phase 2 | Нужны отдельное согласие, storage policy и unit-экономика. | Не загружаются и не показываются в MVP. | Не логировать URL, превью, EXIF или raw metadata. | Требуется отдельная media retention policy. |
| `ClientProfile`, клиентский аккаунт, дневник, переносимая история | `personal`, `fitness-adjacent`, возможно `sensitive / special category` | Phase 2 | Нужны отдельные согласия и client-owned модель. | Не являются MVP-данными; клиент не регистрируется в MVP. | Не должны появляться в MVP-логах как продуктовые payload. | Проектируется отдельно после подтверждения MVP-метрик. |
| `AccessGrant`, granular permissions, invite с подтверждением клиента | `security`, `personal` | Phase 2 | Нужны client-owned профиль и явное управление доступами клиентом. | Не используется в MVP публичной ссылки; тренер закрывает доступ по ссылке. | Если будет добавлено в Phase 2, raw tokens/scopes не логировать. | Retention определяется отдельной моделью прав и privacy. |
| Payments: тариф, subscription status, invoice/payment status, provider ids | `payment`, `personal`, `security`, `internal` | Phase 2 | Требуется договорная база для платежей и отдельные условия. | Не входит в MVP; willingness-to-pay проверяется вручную. | Не логировать платёжные реквизиты и raw provider payload. | Сроки хранения определяются финансовыми и provider-требованиями. |

## Обязательные продуктовые правила

1. В MVP есть один критический путь: trainer signup → client card → plan → public link sent/opened → completion mark → trainer review.
2. Клиент в MVP не регистрируется, не имеет личного кабинета, не управляет `AccessGrant` и не переносит историю между тренерами.
3. Публичная ссылка — технический доступ к конкретному `TrainingPlan`, а не самостоятельная продуктовая модель прав.
4. Публичная страница должна быть минимальной: только план и действие отметки выполнения; без медданных, фото/видео, body metrics и расширенной истории.
5. Raw token, содержимое плана, комментарии и персональные данные не должны попадать в логи.
6. Продвинутая аналитика строится только после проверки MVP-метрик и отдельного решения по Phase 2.
7. Любое расширение в сторону client-owned модели требует отдельного изменения бизнес-scope и обновления [BR-010](../01-business/BR/BR-010-public-plan-link-mvp.md) или нового BR.

## Открытые вопросы для Phase 2

| Вопрос | Почему важно |
|---|---|
| Клиентский аккаунт и client-owned профиль | Нужны перед переносимой историей и управлением доступами клиентом. |
| `AccessGrant` и granular consent | Требуются для нескольких специалистов и отзывов доступа клиентом. |
| История тренировок как собственность клиента | Нужна отдельная модель consent, deletion, export и переносимости. |
| Медданные, body metrics и фото/видео | Требуют юридической проверки, storage policy и отдельной unit-экономики. |
| Биллинг и платежные данные | Нужна интеграция с provider и финансовая retention policy. |
| Расширенная аналитика и отчёты | Нужны отдельные продуктовые гипотезы и защита от неверной интерпретации health-adjacent данных. |
