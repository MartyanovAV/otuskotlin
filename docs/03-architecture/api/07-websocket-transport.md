# WebSocket transport

WebSocket — дополнительный транспорт для тех же версионированных DTO, которые используются POST Full API. Он не вводит новые бизнес-команды и не заменяет OpenAPI-контракты: JSON request/response берутся из соответствующей спецификации v1 или v2.

## Маршруты

Caddy сохраняет внешний префикс bounded context и направляет соединение в Training Service.

| API | Публичный адрес через Caddy | Внутренний адрес Ktor |
|---|---|---|
| Training v1 | `ws://localhost:8080/v1/training/ws` | `training-service:8081/v1/ws` |
| Training v2 | `ws://localhost:8080/v2/training/ws` | `training-service:8081/v2/ws` |

Для production используются те же пути со схемой `wss://` и TLS на внешней точке входа.

## Протокол обмена

1. Клиент устанавливает WebSocket-соединение с маршрутом нужной версии.
2. Сервер выполняет техническую команду `INIT`, регистрирует сессию и отправляет версионированный `InitResponse` с успешным результатом.
3. Клиент отправляет request DTO в текстовом JSON frame.
4. Сервер возвращает соответствующий response DTO в текстовом JSON frame; `requestId` используется для корреляции.
5. В рамках одного соединения можно последовательно отправлять несколько запросов той же версии и того же bounded context.
6. При закрытии сервер выполняет `FINISH` и удаляет сессию из реестра.

Training socket принимает операции `clientCard.*` и `trainingPlan.*`, поддержанные REST-контрактом. V1 frames сериализуются Jackson, v2 — Kotlinx Serialization.

Некорректный JSON или неизвестный request возвращает `InitResponse` с `result=error`, группой `websocket` и кодом `invalid-request`. Binary frame возвращает тот же тип ответа с кодом `unsupported-frame`. Ошибка одного сообщения не закрывает соединение: клиент может исправить request и продолжить обмен. Текст exception и исходный payload наружу не передаются.

## Gateway и авторизация

Оба публичных WS-маршрута защищены тем же Keycloak JWT provider, что и приватный REST API. `Authorization: Bearer <JWT>` передаётся в HTTP Upgrade request и проверяется Caddy до установки соединения. Для WS routes явно включён upgrade `websocket`, а обычный route timeout отключён (`timeout: 0s`).

JWT проверяется при handshake. Текущее соединение автоматически не закрывается в момент истечения `exp`, поэтому клиент должен переподключаться с актуальным token. Caddy принудительно ограничивает длительность одной сессии одним часом, после чего клиент должен переподключиться с актуальным token.

Стандартный browser `WebSocket` API не позволяет задать произвольный `Authorization` header. Для Web UI потребуется отдельное security-решение по доставке token (например, защищённая cookie/BFF); передача JWT в query string в текущей конфигурации не поддерживается из-за риска попадания token в логи и историю.

## Жизненный цикл

Активные сессии хранятся в памяти соответствующего процесса отдельно для v1 и v2. Команды `INIT`, `FINISH` и все прикладные WS-запросы проходят через тот же service processor, что и REST. Сессия добавляется после подключения и удаляется при закрытии соединения. `CorSettings` предоставляет процессору доступ к versioned session repositories, но рассылка доменных событий пока не реализована. Реестр не распределён между репликами и очищается при перезапуске сервиса.

## Текущий режим бизнес-обработки

На текущем этапе процессоры реализуют только stub-фасад. Запрос с `debug.mode=stub` и `debug.stub=success` возвращает фиксированные учебные данные; остальные stub cases формируют контролируемые ошибки. Реальные операции с хранилищем, ownership и доменными правилами ещё не реализованы. Поэтому режимы `prod` и `test` возвращают `not-implemented`, а не маскируются успешными тестовыми данными.

## Транспортные ограничения

| Ограничение | Значение | Назначение |
|---|---:|---|
| Максимальный WebSocket frame в Ktor | 64 КиБ | ограничивает память и чрезмерные payload; превышение закрывает соединение на уровне протокола |
| Ping period / timeout Ktor | 15 с / 15 с | обнаруживает разорванные и зависшие соединения |
| Idle timeout маршрута Caddy | 5 минут | освобождает соединение, по которому нет сетевой активности |
| Максимальная длительность WS в Caddy | 1 час | ограничивает lifetime сессии и обеспечивает периодическое обновление JWT |
| Одновременные downstream-соединения Caddy | 1000 | ограничивает суммарную нагрузку на listener, включая REST и WS |
| Request headers Caddy | 32 КиБ, получение не дольше 10 с | защищает handshake и REST от чрезмерных/медленных заголовков |

Числа являются начальными лимитами локального MVP. Перед production их нужно сверить с размером реальных DTO, числом клиентов и результатами нагрузочного теста.
