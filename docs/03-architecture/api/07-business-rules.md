# API Business Rules

Бизнес-правила API с явной маркировкой MVP, Phase 2 и Design reserve.

#### 3. Бизнес-правила

1. **[MVP] Клиент владеет данными**:
   - `ClientProfile`, `TrainingEntry` и `ProgramAssignment` принадлежат клиенту.
   - `Measurement` и персональные отчёты сохраняются как Phase 2.
   - Тренер получает доступ только через активный `AccessGrant`.
   - Отзыв доступа не требует согласия тренера и применяется немедленно.

2. **[MVP] Модель разрешений AccessGrant**:
   - Минимальные scopes MVP: `PROFILE_READ`, `DIARY_READ`, `DIARY_WRITE`, `PROGRAM_READ`, `PROGRAM_WRITE`.
   - Phase 2 scopes: `MEASUREMENT_READ`, `MEASUREMENT_WRITE`, `REPORT_READ`, `PROGRESS_PHOTO_READ`.
   - По умолчанию доступ запрещён.
   - Расширение scopes всегда требует действия клиента.

3. **[MVP] Приглашения**:
   - Приглашение не является доступом.
   - MVP поддерживает один активный тренерский доступ для клиента.
   - Токен приглашения одноразовый и хранится только в виде хэша.
   - Истёкшие приглашения нельзя принять; нужно создать новое приглашение.

4. **[MVP] Дневник тренировок**:
   - Ручная запись клиента считается источником истины, если не связана с программой.
   - Удаление реализуется мягко, чтобы сохранить аудит и корректность аналитики.
   - Phase 2: изменение тренировочных фактов после создания отчёта инициирует пересчёт затронутых агрегатов.

5. **[Phase 2] Замеры и фото прогресса**:
   - Фото прогресса требуют отдельного разрешения.
   - Медицинские и чувствительные комментарии не попадают в отчёты тренера без соответствующего scope.
   - Нереалистичные значения блокируются валидацией, пограничные значения требуют подтверждения.

6. **[MVP] Простые планы; шаблоны — Phase 2**:
   - Активные назначения используют зафиксированную версию программы.
   - MVP поддерживает только индивидуальные планы без шаблонов и библиотеки упражнений.
   - Архивация шаблона не ломает назначенные клиентам программы.
   - Тренер не может назначить программу клиенту без доступа `PROGRAM_WRITE`.

7. **[Phase 2] Аналитика**:
   - Отчёты не должны раскрывать данные клиента после отзыва доступа.
   - Агрегаты строятся только по видимым пользователю данным.
   - Экспорт истории доступен владельцу-клиенту независимо от текущих тренерских связей.

8. **[MVP] Онбординг тренера**:
   - Минимальный путь: регистрация, заполнение публичного профиля, приглашение первого клиента.
   - Тренерский dashboard не показывает демо-данные как реальные клиентские данные.

9. **[Phase 2] Тарифы и лимиты**:
   - `CLIENT_FREE`: ₽0, клиентский дневник, замеры, принятие приглашений, экспорт собственной истории.
   - `COACH_START`: ₽1 490/мес, до 15 активных клиентов, базовая аналитика, шаблоны программ.
   - `COACH_PRO`: ₽2 990/мес, до 50 активных клиентов, расширенная аналитика, повышенные лимиты приглашений.
   - `STUDIO_TEAM`: ₽5 990/мес, команда/студия, роли, командные шаблоны, лимиты участников по настройке тарифа.
   - Активным клиентом считается клиент с действующим `AccessGrant` к тренеру или команде.

10. **[Phase 2] Платежи**:
    - Платёжные операции должны быть идемпотентны.
    - Webhook платёжного провайдера принимается только с проверенной подписью.
    - При просрочке платежа доступ тренера к существующим клиентам сохраняется на grace period, но новые назначения и приглашения могут быть ограничены.

11. **[Phase 2] Уведомления**:
    - MVP не требует отдельного notification API; статусы приглашений и назначений возвращаются профильными методами.
    - Критические уведомления об оплате, доступах и безопасности нельзя отключить полностью.
    - Уведомления о приглашениях и программах должны иметь ссылку на действие.
    - Повторные уведомления об одном событии объединяются, чтобы не создавать спам.

12. **[MVP] Аудит**:
   - События аудита неизменяемы для ключевых полей.
   - MVP журналирует: выдачу/отзыв доступа, создание приглашений, создание/изменение/удаление записей дневника, назначение планов, отметку выполнения.
   - Phase 2 журналирует: изменение расширенных scopes, экспорт данных, смену тарифа, платежи.
   - Персональные данные в `before`/`after` минимизируются и маскируются, если полное значение не требуется для соответствия.

13. **[Design reserve] Мульти-специалисты**:
    - Каждый специалист получает индивидуальный доступ, а не наследует доступ другого тренера.
    - Координационные заметки видны только участникам care-team с активными ролями.

14. **[Design reserve] Команды студий**:
    - Владелец студии управляет ролями и подпиской.
    - Участник команды не может экспортировать клиентскую базу без роли `OWNER` или `MANAGER`.
    - При удалении участника его клиентские связи требуют передачи или отзыва.
