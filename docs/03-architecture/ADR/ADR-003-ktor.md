# ADR-003: Использовать Ktor для backend

**Статус:** Accepted
**Дата:** 2026-05-19

## Context

FitBridge строится как Kotlin/JVM backend с POST Full API, интеграцией с Keycloak, проверкой доменных доступов, аудитом чувствительных операций и дальнейшим расширением доменных контуров. Для MVP нужен легковесный web framework, который хорошо сочетается с Kotlin, не навязывает тяжёлую инфраструктурную модель и оставляет выбор дополнительных библиотек отдельными архитектурными решениями.

## Comparison

| Criteria | Ktor | Spring Boot |
|----------|:---:|:---:|
| Kotlin-first API design | ✅ | ⚠️ |
| Легковесный runtime для MVP | ✅ | ⚠️ |
| Явная настройка routing/middleware | ✅ | ⚠️ |
| Богатые enterprise conventions из коробки | ⚠️ | ✅ |
| Быстрое подключение только нужных модулей | ✅ | ⚠️ |
| Fit for POST Full API | ✅ | ✅ |

## Decision

Использовать Ktor как backend framework для основного API-контейнера FitBridge. API остаётся Kotlin-приложением на JVM, бизнес-операции публикуются как POST Full JSON endpoints, а интеграции с Keycloak, хранилищами, наблюдаемостью и инфраструктурными библиотеками уточняются отдельными ADR при появлении требований.

## Rationale

- Ktor является Kotlin-first framework и позволяет описывать HTTP API, middleware, сериализацию и обработку запросов идиоматично для Kotlin.
- Легковесная модель Ktor помогает сохранить явные границы между маршрутизацией, доменными контекстами и инфраструктурой.
- Ktor подходит для POST Full API, где важны контролируемая маршрутизация, JSON-контракты и проверка авторизации на каждый запрос.
- Выбор Ktor снижает риск преждевременного включения крупных фреймворк-модулей до уточнения требований.

## Consequences

- Положительно: backend остаётся Kotlin-first и проще удерживает доменную модель отдельно от инфраструктурных деталей.
- Положительно: можно постепенно подключать только необходимые модули для OIDC/JWT, сериализации, валидации, наблюдаемости и persistence.
- Отрицательно: часть интеграций и conventions придётся явно проектировать внутри команды.
- Риск: неоднородность технических решений вокруг Ktor. Митигация: фиксировать дополнительные решения отдельными ADR и поддерживать единые правила структуры backend.
