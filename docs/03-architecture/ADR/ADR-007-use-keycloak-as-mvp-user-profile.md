# ADR-007: Использовать Keycloak как источник identity-профиля MVP

**Статус:** Accepted  
**Дата:** 2026-08-15

## Контекст

Trainer Diary MVP регистрирует только тренера. Критический путь состоит из регистрации, создания `ClientCard` и создания `TrainingPlan`. Выделенный Profile Service содержал только OpenAPI-контракты, транспортные модели и мапперы; runtime-приложение, persistence и самостоятельные доменные правила реализованы не были.

Сервис ещё не опубликован, production-пользователей и production-данных нет. Поэтому решение принимается как greenfield clean break: совместимость со старой моделью, перенос аккаунтов и переходный период не требуются.

Keycloak уже владеет учётной записью, уникальным username внутри realm, credentials, стандартными OIDC profile claims, IAM-статусом и realm roles. Дублирование этих данных в `FITBRIDGE_USER` и `TRAINER_PROFILE` не добавляет MVP-функциональности, но создаёт второй сервис, вторую БД и задачу синхронизации identity-данных.

## Решение

- Удалить Profile Service, Profile API и локальные `FITBRIDGE_USER`/`TRAINER_PROFILE` из MVP.
- Пересоздать локальный realm и начальную схему напрямую в новом виде; не добавлять migration/compatibility layer для несуществующих пользователей.
- Использовать Keycloak `sub` как стабильный owner id в единственном realm `fit-bridge`.
- Отображать `sub` внутри приложения как `AuthPrincipal.userId`, не добавляя custom claim `userId`.
- Использовать `preferred_username` как уникальный логин и отображаемый технический username. Username не используется для ownership.
- Получать роль тренера из `realm_access.roles`; для приватного domain API обязательна роль `TRAINER`.
- Назначать `TRAINER` новым пользователям на стороне Keycloak через default role. Форма регистрации явно сообщает, что создаётся аккаунт тренера, но не принимает роль как доверенное пользовательское значение.
- Получать имя и email через OIDC ID Token/UserInfo. Не обращаться к UserInfo из backend при каждой доменной операции.
- Не включать имя, email и будущую специализацию в access token.
- Хранить в PostgreSQL только доменные данные `ClientCard` и `TrainingPlan`; их `ownerId` равен JWT `sub` и не является внешним ключом на локальную таблицу пользователя.

## Границы решения

- В MVP существует один issuer/realm. При поддержке нескольких issuers каноническим ключом становится пара `(iss, sub)`.
- `specialization` не является обязательным полем критического пути. При появлении подтверждённой потребности короткий атрибут может временно храниться в Keycloak User Profile и выдаваться через UserInfo. Сложный публичный профиль потребует отдельной доменной модели.
- Самостоятельное удаление аккаунта, расширенный consent/deletion flow и клиентская регистрация остаются Phase 2.
- Отключение пользователя не отзывает уже выпущенный self-contained JWT мгновенно. Для MVP используется короткий access-token TTL; более строгая немедленная блокировка потребует introspection или дополнительного состояния.

## Последствия

### Положительные

- Один backend-контейнер и одна прикладная БД вместо двух сервисных контуров.
- Нет синхронизации username, ролей и статусов между Keycloak и локальной user projection.
- Ownership не зависит от доступности отдельного Profile Service.
- Сокращаются сборка, OpenAPI-поверхность и количество тестовых модулей.

### Отрицательные

- Identity-профиль зависит от возможностей и конфигурации Keycloak.
- Профессиональный профиль нельзя бесконечно расширять Keycloak attributes без пересмотра решения.
- Блокировка пользователя начинает действовать для уже выданного access token после его истечения, если не применяется дополнительный механизм отзыва.

## Отвергнутые варианты

1. **Сохранить Profile Service.** Не оправдан критическим путём и текущим объёмом доменной логики.
2. **Сохранить локальную таблицу пользователя внутри Training Service.** Оставляет синхронизацию IAM-статуса без функциональной необходимости.
3. **Использовать username как owner id.** Username предназначен для входа и может иметь иные lifecycle-правила; стабильным идентификатором остаётся `sub`.
