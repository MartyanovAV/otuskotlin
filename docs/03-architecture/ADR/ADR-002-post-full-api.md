# ADR-002: Использовать POST Full API

**Статус:** Accepted
**Дата:** 2026-05-19

## Context

MVP FitBridge содержит командные бизнес-сценарии критического пути: приглашение клиента, выдача и отзыв доступа, назначение простого плана и отметка выполнения упражнений. Распределение этих операций по стандартным HTTP-методам (GET, PUT, DELETE) создало бы неоднородность контрактов и усложнило бы централизованную обработку авторизации, аудита и валидации. Проверка лимитов и биллинг сохраняются как.

## Decision

Все бизнес-операции API выполнять методом `POST` с JSON-телом запроса и JSON-ответом. HTTP-методы `GET`, `PUT` и `DELETE` не использовать для бизнес-операций MVP, оставив их только для вспомогательных задач (например, health-check).

## Rationale

- Единый HTTP-метод упрощает маршрутизацию в Ktor и централизацию cross-cutting concerns: авторизацию, аудит чувствительных операций и валидацию входных данных.
- POST Full подход позволяет передавать сложные команды в теле запроса без ограничений URL и семантики HTTP-методов.
- Упрощается тестирование и документирование API — все бизнес-endpoints следуют одинаковому паттерну запрос/ответ.
- Подход согласуется с CQRS-стилем, где команды (writes) отделены от запросов (reads), что упрощает дальнейшее развитие архитектуры.

## Consequences

- Положительно: единый стиль контрактов для команд и запросов.
- Положительно: проще централизовать авторизацию, аудит и валидацию.
- Отрицательно: стандартная HTTP-семантика кэширования и идемпотентности не используется напрямую.
- Риск: повтор POST-запроса может выполнить команду дважды. Митигация: проектировать idempotency keys для критичных операций.
