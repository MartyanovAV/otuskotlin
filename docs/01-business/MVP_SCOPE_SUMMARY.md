# MVP Scope Summary

## Статус

| Параметр | Значение |
|----------|----------|
| **Статус** | ✅ APPROVE |
| **Дата утверждения** | 2026-05-27 |
| **Комментарий** | Сводный one-page scope выбранного trainer-first MVP с публичной ссылкой FitBridge |

## Business Value

Фиксирует минимальный проверяемый объём FitBridge для Gate 1 после выбора trainer-first MVP с публичной ссылкой. MVP проверяет B2B-ценность для тренера: тренер как единственный зарегистрированный пользователь создаёт клиентскую карточку, создаёт тренировочный план, отправляет публичную ссылку, клиент без регистрации открывает план и отмечает выполнение, тренер видит статус и может закрыть доступ по ссылке.

MVP **не проверяет** полную client-owned модель, регистрацию клиента, личный кабинет клиента, `AccessGrant`, multi-specialist и переносимость истории между тренерами. Эти элементы остаются стратегическим направлением после подтверждения trainer-first ценности.

## MVP Scope

| BR | Что входит в MVP с публичной ссылкой |
|---|---|
| BR-010 | Канонический scope MVP публичного доступа к плану: `ClientCard`, `TrainingPlan`, `CompletionMark`, публичная ссылка, отметка выполнения, статус для тренера, закрытие ссылки |
| BR-004 | Только часть про создание простого тренировочного плана тренером и связь плана с клиентской карточкой; solo-client создание плана не входит в MVP |
| BR-005 | Только базовый статус выполнения для тренера без отдельной аналитики и клиентского кабинета |
| BR-006 | Регистрация тренера, создание первого клиента как карточки, получение первой публичной ссылки на план |
| BR-007 | Не входит в MVP; допускается ручная проверка willingness-to-pay вне продукта |
| BR-009 | Только минимальные privacy-границы для публичной ссылки и запрет чувствительных данных в сценарии публичной ссылки; расширенная consent/deletion модель переносится после MVP |

### Design reserve / pilot only
- **BR-001:** полноценный клиентский дневник, клиентский профиль, самостоятельная регистрация клиента и client-owned история не входят в MVP публичного доступа к плану; остаются Phase 2 / future client-owned scope.
- **BR-002:** `AccessGrant`, явное подтверждение доступа клиентом, отзыв доступа клиентом и granular permissions не входят в MVP публичного доступа к плану; в MVP тренер закрывает публичную ссылку.
- **BR-003:** multi-specialist сценарий не входит в MVP публичного доступа к плану; допустим только как стратегический резерв.
- **BR-008:** командный сценарий студии не входит в MVP публичного доступа к плану; допустимы только design-partner интервью без продуктовой реализации.
- **ADMIN/support для MVP:** полноценного in-product ADMIN/support UI, ЛК администратора и support console нет. Допустимы только controlled operational actions для пилота без чтения чувствительных клиентских данных.
- **BR-005 расширение:** графики замеров, adherence-отчёты, экспорт и premium-аналитика переносятся после MVP.
- **Профильные body metrics:** `heightCm` не входит в MVP required/supported profile fields и переносится в Phase 2 / later measurement scope вместе с замерами и показателями тела.
- **BR-007:** тарифы, лимиты, апгрейд, автоплатежи и dunning переносятся после MVP.
- **BR-009 расширение:** granular consent, продуктовый `AuditEvent`, self-service экспорт данных и расширенная юридическая/аудит-модель переносятся в Phase 2.

### Критический сквозной путь MVP

**Путь: trainer-first сценарий с публичной ссылкой**
1. Тренер регистрируется.
2. Создаёт минимальную карточку клиента.
3. Создаёт простой тренировочный план.
4. Получает публичную ссылку и отправляет её клиенту вне продукта.
5. Клиент без регистрации открывает ссылку, видит план и отмечает выполнение.
6. Тренер видит статус выполнения.
7. Тренер закрывает доступ по ссылке при необходимости.

### Аналитическая воронка MVP

| Этап | Проверяемый сигнал | Что не интерпретировать как MVP-scope |
|---|---|---|
| trainer signup | Тренер готов стартовать без долгого внедрения | Регистрация клиента |
| client card | Тренер создаёт минимальную карточку клиента | Client-owned профиль |
| plan | Тренер создаёт простой план | Библиотека упражнений и шаблоны |
| public link sent/opened | Клиент открывает план без регистрации | `AccessGrant`, invite-flow и клиентский кабинет |
| completion mark | Клиент оставляет отметку выполнения | Полноценный дневник, adherence и отчёты |
| trainer review | Тренер возвращается к статусу и оценивает пользу | Продвинутая аналитика и биллинг |

Метрики воронки используются для решения о Phase 2 client-owned модели, но сами по себе не добавляют в MVP регистрацию клиента, переносимую историю или granular permissions.

## System Constraints

| Constraint | Value | Notes |
|-----------|-------|-------|
| Scope discipline | Только MVP с публичной ссылкой | В MVP входит один критический путь: trainer-first публичный доступ к плану |
| Commercial readiness | Deferred | Биллинг и тарифные ограничения не блокируют Gate 1 |
| Approval state | Approved | Документ утверждён; пересмотр при изменении scope MVP |

## Out of Scope

- Регистрация клиента и личный кабинет клиента
- `AccessGrant`, полноценная модель прав, клиентское подтверждение/отзыв доступа
- Полноценный multi-specialist production-сценарий
- Командный тариф и shared client operations для студий
- AI-генерация программ и продвинутая аналитика
- Шаблоны программ и библиотека упражнений
- Отдельный модуль отчётов, экспорт отчётов и графики замеров
- Тарифы, лимиты, апгрейд, автоплатежи и платёжные напоминания
- Upload/storage фото, видео и любых rich-media материалов; возможен только design reserve/Phase 2
- Привычки, регулярные check-in и rich-media история
- Полноценный club ERP, маркетплейс специалистов и медицинская диагностика
- Отдельный `Notification` API/provider для push/email/lifecycle communications и продуктовый `AuditEvent` API/отдельная audit entity — перенесены в Phase 2; в MVP используется pull-model UI и infrastructure audit-oriented logging через ADR-006.
- Редактирование профиля клиента тренером / trainer `PROFILE_WRITE` для клиентского профиля.
- Требование обязательного заполнения `gender` или `goals` при onboarding без отдельного явного решения о required-статусе.
- `heightCm` как MVP required/supported profile field; рост относится к Phase 2 / later measurement and body metrics scope.
- In-product ADMIN/support роль, личный кабинет администратора, support console, granular operator roles и broad bypass к client profile/diary/training history/health-adjacent data.
- Solo-client PLG путь, самостоятельное создание программы клиентом и переносимость истории между тренерами.
