# Ручное тестирование FitBridge Trainer Diary MVP

Документ содержит воспроизводимые сценарии ручной приёмки локального MVP FitBridge. Основной пользовательский путь: регистрация тренера → карточка клиента → тренировочный план → поиск и повторное использование.

## Статус и область проверки

| Параметр | Значение |
|---|---|
| Статус | Рабочий manual test runbook |
| Область | Trainer-only MVP, UI + публичная граница Envoy + Training API v2 |
| Основной браузер | Последняя стабильная версия Chrome или Edge |
| Приоритеты | `P0` — блокирующий smoke/приёмка; `P1` — обязательная регрессия; `P2` — расширенная проверка |
| Трассировка | [Requirements Traceability Matrix](../02-analysis/REQUIREMENTS_TRACEABILITY_MATRIX.md) |
| Безопасность | [Security Architecture](../03-architecture/SECURITY_ARCHITECTURE.md) |

Не входят в текущий MVP: регистрация клиента, клиентский кабинет, публичные ссылки, биллинг и multi-specialist. Их отсутствие не считается дефектом.

В UI доступны создание, поиск, просмотр и редактирование карточки клиента, а также создание, поиск, фильтрация, просмотр и завершение тренировочного плана. Операции архивирования и редактирования плана присутствуют в API как lifecycle-support, но пока не выведены в UI.

## Правила проведения

1. Использовать только синтетические данные, не содержащие реальные персональные или медицинские сведения.
2. Не прикладывать access/refresh token к баг-репортам и не сохранять его в файлы проекта.
3. Для каждого прогона добавлять уникальный суффикс, например `20260822-qa1`.
4. Перед проверкой безопасности закрыть лишние вкладки и убедиться, под каким тренером открыт браузер.
5. Результат сценария фиксировать как `PASS`, `FAIL`, `BLOCKED` или `NOT RUN`.
6. При `FAIL` приложить шаг, фактический результат, скриншот, время события и `requestId`, если он виден в Network. Токены и пароли на скриншотах должны быть скрыты.

## Подготовка окружения

### Запуск backend-стенда

Из корня проекта:

```powershell
.\gradlew.bat --no-daemon buildInfra
cd deploy
docker compose up --build -d
docker compose ps
```

Ожидается состояние `healthy` у `postgresql`, `keycloak`, `envoy` и `training-service`. Training Service не должен публиковать порт `8081` на хост: внешний доступ к API разрешён только через Envoy.

Проверка доступности:

```powershell
curl.exe http://localhost:8080/health
curl.exe http://localhost:8080/health/training/ready
```

Оба запроса должны вернуть HTTP `200`.

### Запуск frontend

В отдельном терминале:

```powershell
cd fit-bridge-fe
npm ci
npm run dev
```

Открыть `http://localhost:5173`.

### Адреса локального стенда

| Компонент | Адрес |
|---|---|
| Frontend | `http://localhost:5173` |
| Envoy / API / Keycloak routes | `http://localhost:8080` |
| Keycloak Admin Console | `http://localhost:8080/admin/` |

### Тестовые пользователи и данные

Предустановленный smoke-пользователь:

| Поле | Значение |
|---|---|
| Username | `fitbridge-test` |
| Password | `fitbridge` |
| Realm role | `TRAINER` |

Для регистрации и проверки ownership создать двух отдельных тренеров:

- `manual-trainer-a-<suffix>`;
- `manual-trainer-b-<suffix>`.

Пароли должны быть тестовыми и не должны добавляться в Git. Для проверки пользователя без роли создать `manual-no-role-<suffix>` в локальном Keycloak и удалить у него role mapping, через который наследуется `TRAINER`. Не изменять default role realm целиком.

Рекомендуемые прикладные данные:

| Объект                    | Значение                                   |
|---------------------------|--------------------------------------------|
| Клиент A                  | `Клиент A <suffix>`                        |
| Заметка A                 | `Синтетическая заметка <suffix>`           |
| Обновлённое имя           | `Клиент A обновлён <suffix>`               |
| План A                    | `ОФП <suffix>`                             |
| Упражнение                | `Планка`, 3 подхода × 30 повторений, вес 0 |
| Маркер для проверки логов | `SYNTHETIC-SECRET-<suffix>`                |

- пароль не передаётся приложению FitBridge напрямую.

### MT-AUTH-002 — Самостоятельная регистрация тренера

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P0       |
| Покрытие  | RTM-001  |

Шаги:

1. На форме Keycloak выбрать регистрацию.
2. Убедиться, что текст формы сообщает о создании аккаунта тренера.
3. Зарегистрировать `manual-trainer-a-<suffix>` с уникальным email и тестовым паролем.
4. После возврата в приложение открыть «Клиенты» и «Планы».

Ожидается:

- регистрация завершается без ручного назначения роли администратором;
- пользователь входит в приложение и видит кабинет тренера;
- в access token присутствует роль `TRAINER`, но UI не предлагает пользователю самостоятельно выбрать роль;
- access token предназначен для audience `fit-bridge-service`;
- email и имя не обязаны попадать в access token, если доступны через ID Token/UserInfo.

Токен разрешается просматривать только локально в DevTools; его значение не копировать в отчёт.

### MT-AUTH-006 — Обновление истекающего access token

| Атрибут     | Значение                                                                                                                    |
|-------------|-----------------------------------------------------------------------------------------------------------------------------|
| Приоритет   | P1                                                                                                                          |
| Предусловие | Локальное окружение; срок access token временно уменьшен администратором либо тест выполняется после естественного ожидания |

Шаги:

1. Войти и оставить вкладку открытой до момента, когда access token близок к истечению.
2. Не перезагружая страницу, открыть «Клиенты» и выполнить поиск.
3. Повторить запрос после истечения первоначального access token.

После проверки вернуть временно изменённые token lifetimes.

|-----------|---------------------------|

### MT-OWN-002 — Прямой IDOR-запрос к чужому объекту

| Атрибут    | Значение                                                                     |
|------------|------------------------------------------------------------------------------|
| Приоритет  | P1                                                                           |
| Покрытие   | RTM-007                                                                      |
| Инструмент | API client или DevTools с локальными тестовыми сессиями; токены не сохранять |

Шаги:

1. Получить ID карточки тренера A.

### MT-CLIENT-005 — Конфликт optimistic lock

|-----------|----------|
| Приоритет | P1       |

Шаги:

## Тренировочные планы

### MT-PLAN-001 — Создание плана с явным составом

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P0       |
| Покрытие  | RTM-004  |

Шаги:

1. Открыть «Планы» и нажать «Создать план» (либо нажать «Добавить план» из диалога просмотра карточки клиента).
2. Убедиться, что список упражнений пуст и план нельзя сохранить.
3. Ввести `ОФП <suffix>` и выбрать свою карточку клиента (если создается не из карточки).

## JWT, CORS и публичная граница

### MT-JWT-001 — API без access token

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P0       |
| Покрытие  | RTM-007  |

```powershell
curl.exe -i http://localhost:8080/v2/clientCard/search `
  -H "Content-Type: application/json" `
  --data-raw '{"requestType":"clientCard.search","requestId":"manual-no-jwt","clientCardFilter":{"pageSize":10,"pageNumber":1}}'
```

Ожидается: HTTP `401`, заголовок `WWW-Authenticate`; запрос не доходит до доменной операции и не возвращает список.

### MT-JWT-002 — Повреждённый или неподходящий token

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P1       |

Проверить отдельными запросами:

- произвольная строка вместо JWT;
- истёкший JWT;
- корректно подписанный token с другим `aud`;
- token другого issuer.

Ожидается: Envoy возвращает HTTP `401`; `x-jwt-payload` не принимается от клиента как доказательство личности; stack trace и детали ключей подписи не раскрываются.

### MT-CORS-001 — Разрешённый preflight

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P0       |
| Покрытие  | RTM-007  |

```powershell
curl.exe -i -X OPTIONS http://localhost:8080/v2/clientCard/search `
  -H "Origin: http://localhost:5173" `
  -H "Access-Control-Request-Method: POST" `
  -H "Access-Control-Request-Headers: authorization,content-type"
```

Ожидается:

- HTTP `200` без JWT;
- `access-control-allow-origin: http://localhost:5173`;
- разрешены только необходимые `POST,OPTIONS` и `authorization,content-type`;
- ответ формирует Envoy, Training Service не обрабатывает browser CORS.

### MT-CORS-002 — Неизвестный origin

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P0       |

Повторить предыдущий запрос с `Origin: https://untrusted.example`.

Ожидается: HTTP `401` без `access-control-allow-origin`; wildcard `*` отсутствует; запрос не получает доступ только за счёт `OPTIONS`.

### MT-CORS-003 — Фактический browser request

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P1       |

Шаги:

1. В DevTools → Network очистить список.
2. В UI открыть «Клиенты».
3. Найти запрос `/api/clientCard/search` и ответ.

Ожидается: запрос проходит через Vite proxy/Envoy, содержит Bearer authorization, возвращает HTTP `200`; CORS не вызывает `403`; response payload принадлежит текущему тренеру. Значение Bearer token не сохранять.

## Ошибки и восстановление

### MT-ERR-001 — Training Service временно недоступен

| Атрибут     | Значение                                           |
|-------------|----------------------------------------------------|
| Приоритет   | P1                                                 |
| Предусловие | Локальный стенд, нет выполняющихся операций записи |

Шаги:

1. Остановить только `training-service`.
2. Открыть список клиентов.
3. Проверить сообщение и кнопку повторной попытки.
4. Запустить сервис, дождаться healthy и нажать «Повторить попытку».

### MT-ERR-002 — Ошибка домена при HTTP 200

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P1       |

Отправить валидно аутентифицированный запрос с некорректными бизнес-данными, например пустым display name или неправильным lock.

Ожидается: транспортный статус может быть HTTP `200`, но body содержит `result: error` и массив `errors`; UI считает операцию неуспешной, не закрывает форму как при успехе и показывает пользовательское сообщение.

### MT-ERR-003 — Отсутствие дублей при медленном ответе

| Атрибут   | Значение |
|-----------|----------|
| Приоритет | P2       |

С помощью Network throttling замедлить соединение и несколько раз нажать submit при создании карточки/плана.

Ожидается: во время отправки кнопка заблокирована; создаётся не более одного объекта; после ответа форма приходит в согласованное состояние.

## Критерии завершения прогона

Релиз-кандидат допускается к следующему этапу, если:

- все `P0` имеют статус `PASS`;
- нет открытых security-дефектов уровня critical/high;
- все `P1` выполнены либо для каждого `BLOCKED/FAIL` принято явное решение;
- в логах нет токенов, паролей и незамаскированного тестового secret marker;
- не возникло необъяснённых HTTP `5xx`;
- найденные дефекты содержат воспроизводимые шаги и не включают секреты.
