# Documentation Improvement Plan

План фиксирует, что нужно добавить, доработать и переделать в архитектурной, аналитической и бизнес-документации FitBridge.

## Общий вывод

Документационная база уже сильная: есть Vision, Personas, CJM, MVP Scope, BR-001..BR-009, Product Roadmap, FR/NFR, API markdown и ADR по ключевым архитектурным решениям.

Главная задача — поддерживать согласованность scope, метрик, аналитических требований и целевой архитектуры.

## Закрытые / завершённые задачи

История выполненных улучшений свёрнута: канонические источники уже созданы и должны поддерживаться вместо дублирования подробностей в этом плане.

| Область | Канонический источник |
|---|---|
| MVP scope, Solo-client, ADMIN/support boundaries | `docs/01-business/MVP_SCOPE_SUMMARY.md` |
| BR/acceptance criteria, privacy/consent/deletion | `docs/01-business/BR/*.md`, особенно `BR-009-consent-privacy-deletion.md` |
| Traceability | `docs/02-analysis/REQUIREMENTS_TRACEABILITY_MATRIX.md` |
| Data classification, access/logging/deletion rules | `docs/02-analysis/DATA_CLASSIFICATION_MATRIX.md` |
| Roadmap и Phase 2/Phase 3 границы | `docs/01-business/PRODUCT_ROADMAP.md` |

## Актуальные действия

| Что | Нужно сделать | Основания |
|---|---|---|
| Синхронизировать архитектурные решения и модульную модель | Поддерживать единое описание целевой структуры сервиса и границ сущностей | Требуется единый источник правил по структуре модулей |
| Уточнить границы MVP и Phase 2 в связанных документах | Поддерживать единые формулировки по API, данным, ролям и метрикам | Требуется регулярная проверка связей между BR, FR/NFR, RTM и roadmap |
| Создать машиночитаемые контракты API | Написать `openapi.yaml` для `/v1/*` методов | Необходимо для автотестов (RTM) и синхронизации front/back |
| Выбрать UI-фреймворк | Принять решение (React/PWA/KMP/др.) и выпустить ADR по Frontend | Влияет на архитектуру авторизации (Keycloak) и offline-дневник |
| Формализовать Runbook для Support | Описать технический формат операций (bash, CLI, SQL CI/CD) | В MVP запрещён admin UI, но операции без доступа к БД нужны |
| Уточнить сбор продуктовых метрик | Выпустить ADR или раздел по интеграции аналитики | OpenSearch (ADR-006) покрывает только аудит, а не продуктовую воронку |
| Решить проблему версионирования программ | Выбрать между Snapshot (копирование) и Version Link в БД | Изменение шаблона не должно ломать историю тренировок клиента |
| Описать проверку Willingness-to-Pay | Уточнить механику ручного выставления счетов для пилота | Биллинг исключён из MVP, но метрика 5 платящих тренеров есть |

## Поддерживать / monitoring

Проверять при изменении scope, BR, FR/NFR, API, roadmap или архитектурных решений.

| Приоритет | Область | Что поддерживать |
|---|---|---|
| P0 | Traceability и acceptance | Стабильные `RTM-*`, связь с BR/AC/API/тестами; негативные сценарии не удалять. |
| P0 | Privacy/data | `BR-009` и `DATA_CLASSIFICATION_MATRIX.md`: согласия, доступ, логирование, удаление, границы health-adjacent данных. |
| P0 | MVP/Phase 2 boundaries | Канон MVP в `MVP_SCOPE_SUMMARY.md`; Phase 2 — в `PRODUCT_ROADMAP.md` и соответствующих BR. |
| P1 | Метрики | Канон: activation ≥55%, invite acceptance ≥45%, первая отметка ≥50%, первая запись дневника ≥70%, willingness-to-pay ≥5 пилотных тренеров. |
| P1 | API contracts и проверяемость | Добавить OpenAPI/JSON Schema или единый contract; при автоматизации привязать тесты к RTM. |
| P2 | Язык и формулировки | Убирать нетестируемые формулировки и смешение RU/EN заголовков при очередных правках. |

## Рекомендуемый порядок работ

1. Не возвращать завершённые P0-пункты в активный backlog без нового решения по scope.
2. Сначала поддерживать канонические источники, затем обновлять сводные документы и ссылки.
3. Плановые улучшения: добавить validation plan, machine-readable API contracts и привязку автоматизированных тестов к RTM.
