# TDD Process

## Когда TDD обязателен

Применяй TDD для:

- исправления бага;
- новой бизнес-логики;
- изменения наблюдаемого поведения или контракта.

Не требуй искусственный RED-цикл для документации, форматирования, механического rename, чистого рефакторинга без изменения поведения и конфигурации без исполняемого поведения. Для них выполни подходящую статическую или интеграционную проверку.

## Выбор уровня теста

| Изменение | Основной уровень |
|-----------|------------------|
| Бизнес-правила и use cases | `biz` unit/domain tests |
| Mapper, DTO, serialization, API contract | mapper/API contract tests |
| Ktor routing, plugins, persistence wiring | `app-ktor` integration tests |
| Межсервисное или внешнее API-поведение | E2E после более узких тестов |

## Подготовка теста

1. Изучи контракт и существующие тесты.
2. Определи позитивный, негативный и граничный сценарии, релевантные изменению.
3. Выбери минимальный уровень, на котором воспроизводится наблюдаемое поведение.
4. Используй моки только на внешних или недетерминированных границах: сеть, БД, брокер, clock/randomness, сторонний API. Для собственной доменной логики предпочитай реальные объекты, in-memory fake или state verification.

## Цикл Red-Green-Refactor

### RED

До добавления теста по возможности проверь, что релевантная существующая suite зелёная. Затем добавь один целевой regression/behavior test и запусти узкую задачу:

```bash
./gradlew -p <affected-build> :<affected-module>:<test-task> --console=plain
```

Новый тест должен падать по ожидаемой причине. Требование «все тесты должны упасть» неверно: посторонние существующие тесты должны оставаться зелёными. Если тест проходит до реализации, он не доказывает требуемую регрессию — исправь setup или assertion.

### GREEN

Внеси минимальное изменение, необходимое для прохождения целевого теста. Не добавляй несвязанный scope и не ослабляй assertion ради зелёного результата.

### REFACTOR

После GREEN убери дублирование, уточни имена и структуру, не меняя поведение. Повтори целевой тест, затем выполни обязательные для scope более широкие ступени verification ladder.

## Чеклист готовности

- [ ] TDD применён к изменению поведения либо исключение обосновано?
- [ ] Выбран правильный уровень теста?
- [ ] Новый целевой тест падал до реализации по ожидаемой причине?
- [ ] Существующие тесты не получили посторонних падений?
- [ ] Моки ограничены внешними границами?
- [ ] После GREEN не ослаблены assertions?
- [ ] После рефакторинга пройдена verification ladder?
